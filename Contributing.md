# Общий Workflow для контрибьютора

- Обратиться в чат с предложением по контрибьюту (по уже рассмотренной задаче или по новой).
- Получить согласие на доработку от команды библиотеки (в ходе обсуждения в чате: анализ задачи, ее необходимости).
- Клонировать репозиторий.
- Создать ветку для задачи.
- Установить зависимости (npm install).
- Разработать компонент или исправить баг.
- Написать тесты при необходимости.
- Обновить документацию (проверить документацию самого компонента, его пропсов и тп.).
- создать или обновить story (для компонента и протестировать корректность работы кода)
- Создать Pull Request.
- Пройти ревью кода.

- Дождаться мерджа.

## Как установить и запустить проект локально

1. В терминале `git clone https://stash.dddddd.ru/scm/uvhd-fiori/digital_finance_ui.git .`
2. В терминале `git checkout develop`
3. В терминале `npm ci --ignore-scripts`
4. Запуск проекта storybook: в терминале `npm run storybook --verbose`
5. Перейти по [ссылке](http://localhost:4400/)

## Как создать Pull Request (PR).

1. `git checkout develop` - переходим на дев ветку (ветвимся от ветки `develop`)
2. `git pull origin develop` - актуализируем ветку
3. `git checkout -b feature/component(or feature)-name` - для разработки новых компонентов и фичей
   или `git checkout -b bugfix/issue-name` - для исправления багов.
4. Разрабатываем фичу в данной ветке
5. Commit-им изменения (придерживаемся соглашения в рамках проекта - следующий параграф)
6. Создаем pull request со `своей ветки` в ветку `develop`, указав не менее 2 ревьюеров.

## Соглашение по commit-message

На проекте мы используем соглашение совместимое с [Conventional Commits][link1].

Сообщения коммитов должны быть следующей структуры:

Формат:
`<тип>(контекст): <опционально JIRA-ID> <описание>`

1.  Типы изменений

Коммит должен начинаться с типа, который является существительным:

_Публикуемые в changelog изменения._

| Тип         | Описание                |
| ----------- | ------------------------ |
| `feat`      | Новая функциональность  |
| `fix`       | Исправление ошибки      |
| `refactor`  | Рефакторинг кода        |
| `test`      | Изменения тестов        |
| `docs`      | Обновление документации |
| `ci`        | Изменения CI/CD         |

_Непубликуемые (nfp - not for publish) в changelog изменения._

| Тип             | Описание                |
| ---------------- | ------------------------ |
| `nfp-feat`      | Новая функциональность  |
| `nfp-fix`       | Исправление ошибки      |
| `nfp-refactor`  | Рефакторинг кода        |
| `nfp-test`      | Изменения тестов        |
| `nfp-docs`      | Обновление документации |
| `nfp-ci`        | Изменения CI/CD         |

_Критические изменения (BREAKING CHANGE)._ Это не отдельный тип в заголовке, а отдельная строка в **теле** коммита — именно так её распознаёт наш release-инструмент (lerna + conventional-commits) при подсчёте major-версии:

```
feat(Table): убран deprecated-проп colorScheme

BREAKING CHANGE: проп colorScheme больше не поддерживается, используйте theme
```

2.  Структура

`<тип>(контекст): <опционально JIRA-ID> <описание>`

- **контекст**: описывает часть кодовой базы, которую затронул коммит, записывается в круглых скобках (`auth`, `button`)
- **опционально JIRA-ID**: опционально. Номер задачи в [jira](https://jira.dddddd.ru/secure/RapidBoard.jspa)
- **описание**: кратко на русском с маленькой буквы

3. Примеры

```
feat(Table): добавлен новый функционал MassActionPanel

nfp-docs(DrawerDF): в story поправлены отступы между основными блоками
```

## Требования к коду (стиль, линтеры, тесты).

- **Документация** документируйте каждый компонент (пропсы, примеры использования пропсов и описание самого компонента: для чего и тп.).
- **Примеры использования** после разработки фичи или компонента - добавьте примеры использования компонентов в Storybook.
- **Для стилизации** используем `styled-components`.
  Для значений свойств стилей (цвета, отступы, скругления) стараемся использовать токены из `@ui-kit/tokens`.
- **В качестве линтера** используем eslint. С конфигурацией линтера в проекте можно ознакомиться [здесь](./.eslintrc.json). Стараемся следовать всем правилам. Если какие-то правила считаете не нужными или хотите
  добавить новые правила, то поднимаете вопрос-проблему в чате, и в случае получения согласия внедряете изменения через pull request.
- **Ненужные комментарии** в коде стараемся не оставлять. Оставляем комментарии, которые могут быть полезными. И добавляем описание: где и для чего может понадобится закомментированный код или комментарии.
- **Тесты** относимся к тестам всегда положительно, особенно в местах, где они крайне необходимы.

## Процесс ревью кода.

- Ревью кода должен производиться не менее 2-мя разработчиками библиотеки компонентов.
- В процессе ревью соблюдаем уважение, и любые комментарии должны быть в формате совета или вежливого направления в нужное русло.
- Получив комментарии, если согласны, то правите и обновляете код в своей ветке с фичей.
  А если не согласны, то можно аргументировать свою позицию соблюдая уважение. И спорный момент закроется На этом или решение найдется в ходе обсуждения.
