# Скриншотные тесты

Storybook test-runner выполняет рендер и `play`, затем Playwright снимает страницу,
а pngjs/pixelmatch сравнивают её с PNG-эталоном. Поддерживаются DOM и Canvas.

## Окружение

Проверка и обновление эталонов выполняются в Docker: Linux amd64, Chromium и
Playwright зафиксированных версий, одинаковые viewport, масштаб и локальные SBSans.
Нужны Docker с Compose v2 и Node.js >=20. Отдельный сервер Storybook не нужен.
При первой сборке Docker скачивает базовый образ и зависимости. Шрифты уже хранятся
в репозитории; сами тесты работают без сети.

`docker.js` выполняется на компьютере разработчика или GitHub runner. `build.js`
собирает стенд при сборке образа, а `run.js` запускает его внутри контейнера.
Dockerfile генерирует метаданные Storybook перед проверкой типов, поэтому первый
запуск работает и в чистом checkout без локальных `types.string.json` и `functions.string.json`.
Внутренний адрес `127.0.0.1:4400` используется сервером и браузером в одном контейнере;
порт не публикуется на хост и не конфликтует с локальным Storybook. Адрес и порт
заданы вместе в `run.js`. `transaction.js` переносит эталоны на хосте после update.

Локальные SBSans взяты из [набора Plasma](https://github.com/salute-developers/plasma/tree/c13feb4d78c772f5d9aaae2a62c78329e1df2d52/cypress/fixtures/fonts).
Они находятся в `packages/storybook/static/screenshot-fonts/` вместе с `fonts.css`.
Контрольные суммы локальных файлов шрифтов и CSS входят в `environment.json`,
чтобы изменение этих ресурсов не смешивалось со сравнением прежних эталонов.

В тестовом браузере задан `reducedMotion: 'no-preference'`: системная настройка
компьютера не влияет на stories. Конечные анимации завершаются перед PNG средствами
захвата. Продуктовые стили ради скриншотов не выключают анимацию.

## Команды

| Команда                                     | Назначение                                             |
| ------------------------------------------- | ------------------------------------------------------ |
| `npm run screenshot:test`                   | Одно сравнение всех сценариев с эталонами              |
| `npm run screenshot:test -- TableCanvas`    | То же, только подходящие story-файлы                   |
| `npm run screenshot:update`                 | Создать полный новый набор эталонов                    |
| `npm run screenshot:update -- CanvasAvatar` | Обновить выбранные эталоны, сохранив остальные         |
| `npm run screenshot:typecheck`              | Проверить типы screenshot-кода                         |
| `npm run storybook:build:screenshots`       | Собрать тестовый Storybook; обычно вызывает Dockerfile |

Фильтр — регулярное выражение пути **story-файла**, не идентификатор отдельной story.
Пустая выборка считается ошибкой. `test` и `update` используют один runner; обе
команды сначала собирают Docker-образ с использованием кэша.

Проверка не повторяет упавший тест и не меняет эталоны. Обычный `test` сохраняет
снимки, различия и HTML-отчёт для разбора ошибки. При подозрении на нестабильность
повторите ту же адресную команду вручную: каждый запуск создаёт новый контейнер
и браузер, а его результат и артефакты сохраняются отдельно.

## Работа над изменением

1. Изменить компонент и подходящую story. Если нужно проверить взаимодействие,
   добавить действия и проверки в `play`: PNG сам по себе проверяет только итоговый
   вид, а не выполнение клика или другого действия.
2. Запустить адресный `npm run screenshot:test -- <фильтр>` и открыть отчёт.
   Для новой story отсутствие эталона ожидаемо, но ошибки render, `play` и ресурсов
   сначала нужно устранить.
3. Если различие намеренное, выполнить `npm run screenshot:update -- <фильтр>`,
   просмотреть новые и изменённые PNG, затем повторить тот же `screenshot:test`.
   Закоммитить код и проверенные эталоны вместе.
4. При необходимости запустить ручной CI для ветки PR по инструкции ниже.

При изменении общих правил захвата, окружения, шрифтов или компонентов, влияющих
на множество stories, нужен полный compare. Если меняется само окружение, сначала
подготовить и просмотреть полный новый набор эталонов, затем выполнить полный
compare. Для изменений только Markdown Docker-прогон не нужен.

## Когда обновлять эталоны

Сначала открыть `artifacts/screenshots/<запуск>/run-1/index.html` и проверить различия.
Если внешний вид изменён намеренно, выполнить адресный `screenshot:update -- <фильтр>`
и проверить PNG в diff. Пустой Canvas или случайно сломанная вёрстка не должны
становиться новым эталоном.

Новые PNG сначала сохраняются отдельно. Замена каталога эталонов происходит только
после успешного завершения всех выбранных сценариев и проверки полноты результатов.
Полное обновление удаляет устаревшие PNG; адресное сохраняет остальные.
При несовпадении `environment.json` с окружением контейнера compare и адресное update
останавливаются: необходим проверенный полный набор для нового окружения.

В Git хранятся `packages/storybook/__snapshots__/*.png` и `environment.json`.
HTML/JSON-отчёты запусков, diff и временные файлы остаются в игнорируемом `artifacts/`.
Стили внутри `index.html` оформляют только отчёт и не влияют на тестируемые stories.

## Как получается снимок

1. Проверяются Chromium/SwiftShader и загрузка шрифтов до рендера story.
2. Выполняется `play`, проверяются ошибки загрузки изображений и шрифтов.
3. Захват дожидается ресурсов, завершает конечные анимации и запрашивает полную
   перерисовку подключённых Canvas-таблиц; после этого ждёт два кадра браузера.
4. Требуются три попарно одинаковых по правилам сравнения кадра в одном бюджете
   10 секунд. Это ожидание готовности, а не перезапуск тестового сценария.
5. PNG сравнивается с эталоном. `threshold: 0.02` — чувствительность к отличию цвета
   пикселя, **не 2% допустимых отличающихся пикселей**. `includeAA: false` исключает
   распознанные различия сглаживания. Допустимых отличий после этих правил — ноль;
   изменение размера также считается ошибкой.

## Ограничения и разбор нестабильности

Ранее воспроизводился редкий пустой промежуточный кадр Canvas, после которого
следующие кадры были нормальными и тест проходил. Причина этого сбоя не установлена.
Три стабильных финальных кадра и успешный compare не доказывают отсутствие такого
промежуточного дефекта. Если он повторится, сохраняйте условия и артефакты для
адресной диагностики; не принимайте пустое изображение как новый эталон.

Захват стабилизирует CSS/Web Animations, но не останавливает произвольную анимацию
через JavaScript или `requestAnimationFrame`. Для неё нужен детерминированный
сценарий или обоснованный PNG-skip. Не увеличивайте допуски, не добавляйте пропуски
и не обновляйте PNG только для устранения красного статуса. Число фактически
проверенных сценариев, PNG и пропусков берите из отчёта конкретного запуска.

## Настройки story

```ts
parameters: {
  screenshot: {
    // Сохранить наведённое или выбранное в play состояние указателя.
    keepState: true,
    // Необязательно: захватить всю страницу вместо #storybook-root.
    capture: 'page',
  },
},
```

`skip: true` пропускает только PNG, сохраняя render и `play`. Обязателен `skipReason`
с конкретной причиной на русском. Пропуск означает отсутствие визуального покрытия.

`allowedResourceErrors: ['/canvas-images/missing.png']` разрешает ожидаемую ошибку
загрузки в сценарии проверки fallback. Значения — подстроки URL. Это исключение из
проверки ресурсов и ожидания DOM-изображений; остальные ресурсы и сравнение PNG
проверяются как обычно. Не использовать общий путь для сокрытия случайных ошибок.

## Файлы реализации

| Файл                                          | Назначение                                                       |
| --------------------------------------------- | ---------------------------------------------------------------- |
| `scripts/screenshots/docker.js`               | Команда на хосте: образ, контейнеры, фильтр, применение эталонов |
| `scripts/screenshots/run.js`                  | Сервер внутри контейнера, запуск Jest, отчёт и проверка полноты  |
| `scripts/screenshots/build.js`                | Чистая сборка через Storybook CLI и проверка её результата       |
| `scripts/screenshots/transaction.js`          | Замена эталонов с откатом при ошибке                             |
| `packages/storybook/static/screenshot-fonts/` | Локальные SBSans и CSS подключения для тестового стенда          |
| `.storybook/test-runner.ts`                   | Подготовка story, захват и запись результата                     |
| `test/screenshots/capture.ts`                 | Готовность ресурсов и стабильность кадров                        |
| `test/screenshots/compare.ts`                 | Сравнение PNG, diff и составное изображение                      |
| `test/screenshots/environment.cjs`            | Диагностика ошибок до вызова postVisit; формат загрузки Jest     |
| `.storybook/decoratorCanvasSnapshots.tsx`     | Подключение тестовой команды перерисовки Canvas                  |

Пути последних пяти строк указаны относительно `packages/storybook/`.
`STORYBOOK_SCREENSHOT_TEST=1` включает отдельную конфигурацию тестовой сборки:
визуальные stories, локальные картинки/шрифты и декоратор перерисовки Canvas.
Обычная сборка Storybook использует прежнюю конфигурацию.

## PR и CI

Workflow [Screenshots](../../../.github/workflows/screenshots.yml) запускается
**только вручную** и выполняет ту же команду `screenshot:test` в Docker на Ubuntu x64.
Он не обновляет эталоны, не повторяет упавшие тесты и не назначается обязательной
проверкой для слияния PR. При ошибке запуск остаётся красным.

Для ручного запуска через интерфейс GitHub файл workflow должен сначала попасть
в default branch `main`. В этом репозитории путь внедрения — PR в `develop`, затем
PR из `develop` в `main`. До этого сравнение можно запускать локально в Docker.
Это [требование GitHub для workflow_dispatch](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).

После появления workflow в `main`:

1. Открыть **Actions → Screenshots → Run workflow**.
2. В **Branch** выбрать ветку проверяемого PR. В ней должны быть workflow,
   screenshot-код и совместимые PNG-эталоны с `environment.json`.
3. В поле **filter** указать путь или регулярное выражение, например `CanvasAvatar`
   либо `TableCanvas`. Пустое поле запускает все сценарии.
4. Открыть завершённый запуск и скачать artifact `screenshots-<run_id>-<attempt>`.
   После распаковки открыть `<запуск>/run-1/index.html` рядом с папками изображений.
   `ci.log` содержит вывод команды, включая ошибку ранней сборки, если PNG ещё нет.
5. При намеренном изменении внешнего вида обновить нужные эталоны локально,
   проверить diff и закоммитить PNG в ту же ветку. Повторить ручное сравнение.

Артефакты хранятся семь дней и загружаются также при падении тестов. Если запуск
не дошёл до тестового шага, например не удалось получить исходники, файлов может
не быть. Лимит задания — 45 минут. Новый ручной запуск той же ветки отменяет
предыдущий независимо от выбранного фильтра.

Зависимости устанавливает Dockerfile: отдельный `npm ci` на GitHub runner не нужен.
Внешняя сеть требуется на этапе сборки; тестовый контейнер работает без неё.
Между заданиями на разных GitHub runner кеш Docker автоматически не сохраняется,
поэтому время первого пилота включает сборку образа и Storybook.
