# CellsMerging: справочник

Подробности объединения ячеек: совмещение способов, составные ключи, работа с
деревом, взаимодействие с остальными фичами таблицы, выравнивание и сводный
список ограничений. Обзор способов и живые примеры — на странице
[Docs](?path=/docs/локальные-компоненты-tablecanvas-cellsmerging--docs), типы —
на странице
[API](?path=/docs/локальные-компоненты-tablecanvas-cellsmerging-api--docs).

## Если включено несколько способов сразу

Способы можно совмещать в одной таблице — правила простые и считаются по колонке:

- Если колонка входит хотя бы в один регион из `mergedCellsRegions`, её
  объединения описывают только регионы. `mergeByCellValues` на этой колонке не
  действует.
- Колонка merged-вида (группировки или subRows) сливается по границам групп.
  Пользовательский `mergeByCellValues` на той же колонке не действует — иначе два
  механизма спорили бы за одни ячейки.
- В остальных случаях работает `mergeByCellValues`.
- Разные колонки живут независимо: регион на одной колонке и слияние по значению
  на другой — обычная рабочая комбинация.

Пример: таблица с группировкой по «Отделу» (merged-вид) может дополнительно
сливать колонку «Статус» через `mergeByCellValues`, а строки-заголовки секций
рисовать регионами на всю ширину — все три способа уживаются, потому что заняты
разными колонками.

## Объединение по значению: где проходит граница

У `mergeByCellValues` есть классическая ловушка. Допустим, регионы «Север» и «Юг»,
и в каждом есть «Команда 1» и «Команда 2»:

```
Север | Команда 1 | Иванов
Север | Команда 2 | Петров
Юг    | Команда 2 | Сидоров
Юг    | Команда 1 | Смирнов
```

Если сливать колонку команды по её значению, «Команда 2» из Севера и «Команда 2»
из Юга стоят рядом — и сольются в один блок через границу региона. Визуально это
выглядит как ошибка: одна команда, а на деле две разные.

Решение — сливать не по тексту в ячейке, а по составному ключу, в котором зашит
путь от корня:

```tsx
mergeCells: {
  mergeByCellValues: [
    'region',
    // Сравнивается результат функции, а не текст в ячейке.
    { colKey: 'team', value: (row) => `${row.region} / ${row.team}` },
  ],
}
```

Теперь у «Команды 2» из Севера ключ «Север / Команда 2», а у южной —
«Юг / Команда 2». Ключи разные, слияние останавливается на границе региона само,
без какой-либо отдельной логики. В ячейке при этом показывается обычное значение
колонки — функция влияет только на сравнение.

В полном примере (стори «mergeByCellValues: пример с серверными данными») такие
ключи собраны заранее в полях строки: `divPath`, `unitPath`, `teamPath` — по
одному на каждый уровень иерархии.

Merged-виды группировки и subRows строят такие ключи сами — там об этой ловушке
думать не нужно.

## Дерево через subRows: как передавать данные

Разберём подробнее самый ёмкий сценарий — `subRows` с `view: 'merged'`.

### Какое дерево ждёт таблица

В `rows` передаются корневые узлы, детей таблица достаёт через `getSubRows`.
Роли узлов распределены так:

- **Внутренние узлы** (дивизион, управление, команда) — ярлыки уровней. Каждый
  несёт поле с именем своей колонки из `mergedColumns`: узел дивизиона — поле
  `division`, узел управления — поле `unit`, и так далее.
- **Листья** — строки данных. Именно они становятся строками таблицы со своими
  показателями; внутренние узлы отдельными строками не показываются.

```tsx
const tree = [
  {
    id: 'd1',
    division: 'Розничный бизнес', // узел уровня 0
    subRows: [
      {
        id: 'u1',
        unit: 'Управление продаж', // узел уровня 1
        subRows: [
          {
            id: 't1',
            team: 'Команда Север', // узел уровня 2
            subRows: [
              { id: 'e1', employee: 'Иванов', plan: 100, fact: 90 }, // лист
              { id: 'e2', employee: 'Петров', plan: 80, fact: 85 },
            ],
          },
        ],
      },
    ],
  },
];
```

```tsx
tableConfig={{
  subRows: {
    view: 'merged',
    mergedColumns: ['division', 'unit', 'team'], // порядок = уровни дерева
    getSubRows: (row) => row.subRows,
    rowKeyGetter: (row) => row.id,
  },
}}
```

`mergedColumns` — это соответствие уровней дерева и колонок: первый элемент
показывает узлы верхнего уровня, второй — следующего, и так далее. Колонка
`division` возьмёт значение из узла дивизиона и сольётся на все его листья,
`unit` — на листья своего управления, вложенно.

Сворачивания в этом виде нет: таблица показывает всё переданное дерево целиком.
Хотите меньше строк на экране — передайте меньший кусок дерева (следующий
раздел).

### Пагинация по верхним блокам

Дерево у вас, поэтому страницы нарезаете вы — по верхним узлам. Таблице отдаётся
срез дерева, а в `pagination.count` — общее число верхних узлов:

```tsx
const [page, setPage] = useState(1);
const [perPage, setPerPage] = useState(2); // дивизионов на страницу
const pageTree = tree.slice((page - 1) * perPage, page * perPage);

tableConfig={{
  pagination: {
    count: tree.length,     // всего верхних узлов, не листьев
    perPage,
    perPageList: [1, 2, 3], // варианты «показывать по» — в блоках
    value: page,
    onChange: (nextPage, nextPerPage) => {
      if (typeof nextPerPage === 'number' && nextPerPage !== perPage) {
        setPerPage(nextPerPage);
        setPage(1);
      } else if (typeof nextPage === 'number') {
        setPage(nextPage);
      }
    },
  },
  subRows: { /* как выше */ },
}}
// ...
rows={pageTree}
```

Страница «2 дивизиона» может содержать разное число строк-листьев — это нормально:
единица пагинации здесь блок, а не строка. По той же причине настройте селектор
«Показывать по»: его стандартные варианты (20/50/100) рассчитаны на строки и для
блоков не имеют смысла — задайте свой список `perPageList` в блоках, как выше,
либо спрячьте селектор (`hasPerPage: false`). Если дерево приходит с сервера
частями, вместо `slice` будет запрос следующей страницы — контракт тот же.

### Редактирование: правки возвращаются листьями

Редактируются листья. В `editing.onRowsChange` приходят изменённые строки-листья —
записать их обратно в своё дерево должен потребитель, например по `id`:

```tsx
editing: {
  rowKeyGetter: (r) => r.id,
  onRowsChange: (updatedLeaves) => {
    const byId = new Map(updatedLeaves.map((r) => [r.id, r]));
    // Обойдите дерево и замените листья с совпавшими id.
    setTree((prev) => writeLeavesBack(prev, byId));
  },
},
```

Это следствие владения данными: таблица не знает, как устроено ваше дерево,
поэтому отдаёт плоский результат, а раскладываете его вы.

### Что остаётся на вашей стороне

- **Поиск, сортировка, фильтрация** — встроенные механизмы к структурному дереву
  пока не применяются. Отфильтровали или отсортировали своё дерево — передали
  результат в `rows`, таблица показала.
- **Выделение** при этом работает из коробки: один чекбокс на верхний блок, клик
  выделяет все его листья (подробнее — в разделе про выделение ниже).

Живой пример всего вместе — стори «subRows: дерево с пагинацией» на странице
[Docs](?path=/docs/локальные-компоненты-tablecanvas-cellsmerging--docs).

## Объединение и остальные возможности таблицы

Блоки — не отдельный мир: выделение, сортировка, буфер обмена и редактирование
продолжают работать. Здесь собрано, как именно.

### Выделение, нумерация и навигация

Выделение настраивается как обычно — `selecting` со стейтом и `rowKeyGetter`.
А вот ведёт оно себя по-разному в зависимости от способа объединения:

- **Плоский вид с mergeByCellValues** — чекбокс у каждой строки, номер у каждой
  строки. Объединение колонок на выделение не влияет: в стори
  «mergeByCellValues: пример с серверными данными» можно выделить одного
  сотрудника внутри слитого блока.
- **Merged-виды группировки и subRows** — один чекбокс и один номер на группу
  верхнего уровня. Клик по чекбоксу выделяет все строки группы разом, повторный —
  снимает. «Выделить всё» в шапке тоже работает. Счётчик выбранного внизу
  считает строки, а не группы: выделили дивизион из 12 сотрудников — внизу
  «выбрано 12».

Специально настраивать групповое поведение не нужно: таблица включает его сама,
когда активен merged-вид.

Навигация тоже понимает блоки: клик в любую точку блока выделяет его целиком,
рамка фокуса рисуется вокруг всего блока, один шаг стрелкой перепрыгивает блок.
Попасть «внутрь» блока с клавиатуры нельзя — для таблицы это одна ячейка.

### Сортировка, фильтрация, поиск и пагинация

Возможности зависят от того, кто владеет данными.

**mergeByCellValues (плоский вид).** Встроенные сортировка, фильтр и поиск
работают как обычно, а блоки пересобираются после каждого изменения порядка —
объединение всегда отражает текущий видимый список строк. Если данные приходят с
сервера постранично, следите, чтобы сортировка на сервере не разрывала группы:
половина группы на одной странице и половина на другой будут выглядеть как два
отдельных блока.

**rowsGrouping (view: 'merged').** Встроенные поиск, сортировка и фильтры
работают: таблица применяет их к строкам до сборки групп, поэтому группы всегда
собираются из уже отфильтрованного списка. Пагинации нет: группировке нужны все
строки сразу. Сортировку по группирующим колонкам можно снять настройкой
`disableGroupColumnsSort` — как в дереве, где сгруппированные колонки не
сортируются.

Частая ошибка при встроенных фильтрах (не только в этом виде): в стейте
`filtering.state` должен быть ключ каждого фильтра, объявленного в колонках.
Select-фильтр без своего ключа получит пустое значение вместо «показать всё» и
может отсеять все строки — таблица окажется пустой без единой ошибки.

**subRows (view: 'merged').** Дерево у потребителя, поэтому пагинация по верхним
блокам работает: отдаёте страницу дерева — таблица её показывает. Встроенные
поиск, сортировка и фильтрация к структурному дереву пока не применяются — эти
операции делаются на стороне потребителя над его данными.

### Копирование, вставка и протяжка

- Копирование отдаёт значение в позиции верхней-левой ячейки блока, остальные
  ячейки блока в буфере пустые — как в Excel.
- Вставка пишет во весь блок: значение попадает во все его строки.
- Протяжка (fill) растягивается только до целых блоков — залить пол-блока нельзя;
  пунктирная рамка протяжки сама прилипает к границам блоков.

### Редактирование

- Правка ячейки блока записывает значение во все его строки — данные под блоком
  всегда совпадают с тем, что на экране.
- При объединении по значению правка пересобирает блоки: изменили «Отдел» у
  блока — он разъедется или сольётся с соседним, потому что объединение выводится
  из данных.
- У редактируемых Select-ячеек редактор открывается по выравниванию блока: текст
  прижат к низу — редактор откроется у нижнего края, а выпадающий список
  раскроется вверх.

## Выравнивание контента в блоке

По умолчанию контент блока выравнивается по горизонтали как обычная ячейка
этой колонки — из `contentFormat.alignContent` (у числового формата это правый
край), иначе слева. По вертикали — по центру: у обычной ячейки вертикального
выравнивания нет, это чисто блочная настройка. Настраивается лестницей «точечное важнее
общего»:

- `mergedCellsAlign` конкретного региона (только для `mergedCellsRegions`);
- `mergedCellsAlign` на колонке — все блоки этой колонки, работает для всех
  способов включения;
- дефолт фичи: `mergeCells.mergedCellsAlign` или `rowsGrouping.mergedCellsAlign`.

```tsx
columnConfig={[
  { key: 'dept', name: 'Отдел', mergedCellsAlign: { horizontal: 'center', vertical: 'top' } },
]}
```

Колоночный `mergedCellsAlign` может быть и функцией `(row) => MergedCellsAlign`
по данным строки блока — так разные блоки одной колонки получают разное
выравнивание. Это единственный способ управлять выравниванием поблочно в
merged-видах группировки и subRows, где границы блоков решает таблица, а не
потребитель.

```tsx
columnConfig={[
  { key: 'dept', mergedCellsAlign: (row) =>
      row.critical ? { vertical: 'top' } : { vertical: 'center' } },
]}
```

### Свой рендер в блоке

Выравнивание действует на текстовый контент. Кастомный `renderCell` получает весь
прямоугольник блока и выравнивает содержимое сам — через свойства своих
контейнеров.

У колонок со своим рендером есть неочевидность: предпросмотр значения (по
двойному клику на ячейке без редактирования) у них по умолчанию выключен.
Со стороны это выглядит как «у блоков не открывается предпросмотр», хотя дело в
колонке, а не в объединении. Включается настройкой колонки:

```tsx
{ key: 'dept', renderCell: ..., renderCellPreview: 'cellEditorAsPreview' }
```

## Что не работает и почему

Сводный список ограничений. Если «что-то не рисуется» — сначала сюда.

### Во всех способах

- Все ячейки блока обязаны нести одинаковые данные — это контракт
  `mergeByCellValues` (значения реально повторяются в строках) и регионов.
  Причина проста: блок показывает верхнюю-левую **видимую** ячейку, а какая
  ячейка окажется верхней-левой — зависит от закрепления и порядка колонок.
  Если данные одинаковые, блок выглядит одинаково при любой перестановке.
- Попасть «внутрь» блока с клавиатуры нельзя — для таблицы это одна ячейка.
  Это поведение, а не ошибка.
- Выравнивание пока не поддерживает письмо справа налево (RTL).
- Горизонтальная протяжка через colSpan-блок не растягивается до границ блока
  (в работе).
- У колонок со своим `renderCell` по умолчанию выключен предпросмотр значения —
  включается `renderCellPreview: 'cellEditorAsPreview'` (см. «Свой рендер в
  блоке» выше).

### mergedCellsRegions

- Разорванный регион исчезает молча: если после сортировки, перестановки или
  скрытия колонок ключи региона перестали идти подряд, блок просто не рисуется.
  Ошибок и предупреждений нет — следите за порядком сами.

### rowsGrouping (view: 'merged')

- Пагинации нет: чтобы собрать группы, таблице нужны все строки сразу.
- Отдельная колонка «Группировка» не создаётся, поэтому не действует всё, что к
  ней привязано: `groupedColumnProps`, свой контент ячейки группы
  (`renderGroupCell` у колонки) и кнопка «развернуть всё» (`expandAllBtn`) —
  строк-групп и шевронов в этом виде нет.

### subRows (view: 'merged')

- Встроенные поиск, сортировка и фильтрация к структурному дереву не
  применяются — эти операции делает потребитель над своими данными.
- `column.subRow` целиком не действует: шеврон (`isColumnWithArrow`), свой
  контент и ключи вложенных уровней (`renderSubRowCell`, `keyOfColumnInSubRow`,
  `parentKeyAsDefault`, `contentFormat`), свой редактор уровня. Листья рисуются
  как обычные строки — работают их обычные `renderCell`, `contentFormat` и
  `editingCell`.
- `expandedIdsState` и сворачивание не действуют: раскрывать нечего, дерево
  показано целиком.

Это осознанное поведение: один и тот же конфиг `subRows` или `rowsGrouping`
можно переключать между `view: 'tree'` и `view: 'merged'` — лишние настройки
другого вида не мешают. Пометки «работает только в виде дерева» есть и в
подсказках типов.

> Подробнее о типах — [CellsMerging API](?path=/docs/локальные-компоненты-tablecanvas-cellsmerging-api--docs)
