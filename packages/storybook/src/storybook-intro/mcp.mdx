    # Как работать с MCP

    `@daisforge/ui-mcp` — MCP-сервер для `@daisforge/ui`. Работает по stdio и даёт кодовому агенту точные пропсы, типы, категории (wrapper/composition/standalone/form), примеры кода и фичи по всем 243 компонентам библиотеки, 77 фичам и 426 типам — а не только по тем, что описаны в этом Storybook.

    Данные лежат в самом пакете, поэтому сеть в рантайме не нужна. Требуется Node.js 20 или новее.

  </div>
</div>

<div className="sb-container">
  <div className='sb-section-title'>
    # Быстрый старт

    Если агент умеет запускать MCP-серверы по stdio одной командой, достаточно указать:

    <Source
      language='bash'
      dark
      format={false}
      code={`npx -y @daisforge/ui-mcp`}
    />

    Если агент просит `command` и `args` отдельно — такой конфиг (обычно `.mcp.json` в корне проекта):

    <Source
      language='json'
      dark
      format={'dedent'}
      code={`
        {
          "mcpServers": {
            "daisforge-ui": {
              "command": "npx",
              "args": ["-y", "@daisforge/ui-mcp"]
            }
          }
        }
      `}
    />

    Надёжнее — поставить сервер в проект рядом с библиотекой и запускать по локальному пути. Так он не зависит от того, с каким рабочим каталогом клиент его стартует, и всегда видит вашу версию `@daisforge/ui`:

    <Source
      language='bash'
      dark
      format={false}
      code={`npm install -D @daisforge/ui-mcp`}
    />

    <Source
      language='json'
      dark
      format={'dedent'}
      code={`
        {
          "mcpServers": {
            "daisforge-ui": {
              "command": "node",
              "args": ["node_modules/@daisforge/ui-mcp/dist/server.js"]
            }
          }
        }
      `}
    />

    Никаких флагов и параметров у сервера нет: версия библиотеки определяется автоматически — см. «Откуда берутся данные».

  </div>
</div>

    # Какие инструменты доступны агенту

    После подключения MCP-сервер отдаёт агенту девять инструментов:

    + `list_components` — список компонентов с фильтрами по типу (wrapper/composition/standalone/form), категории и scope. По умолчанию показывает только самостоятельные компоненты (~177 из 243): слоты вроде `DrawerDFHeader` и служебные примитивы скрыты, `role: "all"` снимает фильтр.
    + `search_components` — поиск по свободному запросу на русском или английском сразу по трём сущностям: компоненты, их фичи и типы. Ищет и по тексту определения типа, поэтому находит нужное имя, когда оно заранее неизвестно («отрисовать свою ячейку» → `CellContent`/`ColumnConfig`).
    + `get_component` — компактная карточка: тип, категория, подсказка, готовый `importStatement`, имена пропсов, compound-части, список фичей.
    + `get_component_props` — полные пропсы: собственные плюс унаследованные от атомарного компонента `@salutejs/sdds-finai`. Аргумент `part` — для compound-частей, например `Header` у `DrawerDF`.
    + `get_component_examples` — примеры кода компонента. Без `title` отдаёт список заголовков и первый пример, с `title` — конкретный.
    + `get_type` — разворачивает именованный тип из текста пропса. `get_component_props` покажет только имя (`columnConfig: readonly ColumnConfig<Row>[]`), а этот инструмент отдаёт само определение и готовый импорт.
    + `list_features` — список фичей компонента. Особенно актуально для `TableCanvas` и `Table`: у них десятки фичей вроде `Filtering`, `Sorting`, `CopyPasteFill`, до которых иначе не добраться.
    + `get_feature` — документация и API конкретной фичи.
    + `get_feature_examples` — примеры кода конкретной фичи.

  </div>
</div>

<div className="sb-container">
  <div className='sb-section-title'>
    # Ресурсы

    Ещё две вещи сервер отдаёт не инструментами, а ресурсами — это статический контент, который агент читает один раз за сессию, не тратя слот в списке инструментов:

    + `daisforge-ui://catalog/categories` — категории каталога с количеством компонентов по типам.
    + `daisforge-ui://catalog/installation-guide` — установка пакета, подключение стилей и токенов, использование компонентов и иконок.

    Большинство клиентов подтягивают их автоматически, отдельно вызывать ничего не нужно.

  </div>
</div>

<div className="sb-container">
  <div className='sb-section-title'>
    # Откуда берутся данные

    Каталог компонентов собирается из исходников `@daisforge/ui` на релизе и попадает сразу в два места, поэтому сервер ищет его по трём уровням, в таком порядке:

    + **workspace** — каталог из монорепозитория, если сервер запущен внутри него. У потребителей библиотеки не встречается.
    + **installed** — данные из установленной у вас версии `@daisforge/ui`. Основной случай: пропсы гарантированно соответствуют именно вашей версии.
    + **bundled** — запасной каталог, вшитый в сам `@daisforge/ui-mcp`. Включается, если библиотека не установлена или её версия вышла до появления встроенных данных.

    Когда сервер отвечает не из установленной библиотеки, он честно добавляет к ответу поле `dataVersionNotice` — например, что данные соответствуют версии 1.14.1, а у вас установлена другая, и в пропсах возможны расхождения. Если агент это упомянул — обновите `@daisforge/ui`.

  </div>
</div>

    # Что можно спрашивать у агента

    Формулировать можно свободно, называть инструменты не нужно — агент выберет их сам:

    + Какие пропсы есть у `DrawerDF` и как собрать его из compound-частей?
    + Покажи примеры использования `TableCanvas`
    + Какие фичи поддерживает `TableCanvas` и как включить фильтрацию?
    + Нужна таблица с редактированием ячеек и копипастом как в Excel — что взять?
    + Что такое `ColumnConfig` и откуда его импортировать?
    + Какие компоненты есть в категории «Формы»?
    + Как подключить `@daisforge/ui` и глобальные стили в новый проект?

    Последний вопрос особенно полезен в начале работы: агент прочитает гайд по установке и сразу расставит импорты правильно.
