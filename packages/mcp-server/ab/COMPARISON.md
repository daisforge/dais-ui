# Парное сравнение MCP до и после PR #170

[Результаты 126 попыток от 18 ноября 2026](results/pr170-2026-11-18/REPORT.md):
выигрыш в доле компилируемых ответов не подтверждён; сохранены все ответы и ошибки.

Этот стенд измеряет **первую попытку агента написать код с помощью MCP**.
Дополнительный браузерный smoke проверяет начальный рендер, но не всю
бизнес-логику задачи. Стенд не измеряет работу агента после нескольких циклов
исправления ошибок компилятора.

## Зафиксированный эксперимент

- До: `02b45a0fba940038c975fe9db08b10a6e1a9f65c`, база PR #170.
- После: `d49802bb90ea5031578b861a8131d759d30a2ac3`, исправления MCP.
- UI: один собранный пакет `@daisforge/ui@1.29.1`, одни зависимости и TypeScript.
- Задачи: все 21 существующие задачи `ab/tasks.json`, без новых подсказок о
  конкретных исправленных ошибках. `hint` и `expect` не передаются агенту.
- Три независимых сеанса на каждую пару задача/версия: 126 попыток.
- Модель: `gpt-6.2-sol`, reasoning `medium`, Codex CLI; Claude CLI недоступен
  без авторизации. Поэтому старый исторический замер на Sonnet не является
  контрольной группой этого эксперимента.
- Одинаковый prompt, MCP-инструменты, JSON-формат ответа, лимит 420 секунд.
  Порядок версий чередуется внутри пар; одновременно работают три сеанса.
- Модель получает только задачу и MCP. Shell/web/делегирование отключены,
  пользовательский config не загружается, сеансы ephemeral, sandbox read-only.
  Код возвращается текстом и сохраняется раннером. Не-MCP инструменты
  учитываются как нарушение протокола, а не замалчиваются.
- Технический pilot (одна задача на каждую версию) исключён из результатов.
  Основные попытки не выбираются по удачности и не заменяются лучшими.

## Что различается между группами

Сервер MCP и индекс соответствующей версии. `compare-prepare.mjs` пакует
серверы и ставит одинаковый UI tarball. Поскольку `resolveIndex` предпочитает
индекс из установленного UI, **только** `mcp-data/component-index.json` внутри
двух копий UI заменяется на индекс соответствующей группы. JS, `.d.ts` и
зависимости UI одинаковы. Перед запуском проверяются `source: installed`,
версия UI и SHA-256 фактически выбранного индекса; одинаковые индексы — ошибка
стенда. Старый индекс пересобран старым индексером по той же базе UI.

## Метрики и ограничения

Основная метрика — доля всех запланированных попыток, код которых проходит
TypeScript strict против **собранных деклараций пакета**, без source aliases.
Ошибки, вызванные неверным индексом, не вычитаются: они тоже мешают потребителю.
Отсутствие ответа не считается успехом. Сбои авторизации/транспорта останавливают
прогон и сохраняются отдельно, не маскируясь под качество модели.

Дополнительно считаются:

- Прохождение `tsc` с защитными условиями: использован JSX библиотеки, есть
  именованный экспорт, нет явного `any`, подавления диагностики, приведения
  типов (кроме `as const`), не-MCP инструментов и ошибок завершения сеанса.
  Это консервативный фильтр, **не доказательство выполнения требований задачи**.
- Число диагностик, выбор хотя бы одного профильного компонента, вызовы и ошибки
  MCP. Ошибкой MCP считается также JSON с полем `error` без `isError`: иначе
  старый сервер получил бы преимущество за неправильное обозначение отказов.
  Счётчик пересчитывается из сырых транскриптов одинаково для обеих групп.
  Это число неуспешных вызовов, включая неверные аргументы агента, а не число
  доказанных багов MCP-сервера.
  Выбор компонента также не доказывает правильность его использования.
- Время попытки, входные/кэшированные/выходные токены. Входные токены суммируются
  по ходам и включают повторно переданный контекст, это не размер уникального
  контекста. Стоимость в долларах через подписку ChatGPT не оценивается.
  Для времени и вызовов приводятся также медианы: единичные длинные поиски
  не удаляются из выборки и могут сильно влиять на среднее.
- Парная разница «после минус до» и 95% percentile bootstrap-интервал:
  5000 выборок задач с возвращением, внутри каждой сохраняются все повторы
  и обе версии. 63 попытки одной версии не считаются 63 независимыми задачами.

Времена зависят от нагрузки сервиса/машины и кэша; версия модели зафиксирована
именем, но серверная реализация может меняться. Выборка небольшая, из одного
набора задач, на одной модели. Результаты не доказывают выигрыш для всех
пользовательских задач, агентов и сценариев доступа к исходникам.

Скорер отдельно сохраняет повторные запросы провайдера из stderr Codex и
назначенные задержки повтора (`scheduledProviderRetrySeconds`). Это не замер
чистого времени работы MCP: задержки не вычитаются из wall time как будто
известно точное активное время. Попытки с ними остаются в основной выборке.

## Воспроизведение

В двух отдельных checkout должны быть установлены одинаковые зависимости,
собраны MCP-серверы и индексы. В checkout «после» дополнительно собирается UI:

```bash
npm run mcp:build-index
NX_DAEMON=false NODE_ENV=production npx nx build ui-kit
```

Полные декларации UI требуют настоящую установку зависимостей: симлинк всего
`node_modules` в другой checkout может вызвать TS2742 при declaration emit.

```bash
node packages/mcp-server/ab/compare-prepare.mjs \
  --before /path/to/before --after /path/to/after --root /tmp/new-mcp-comparison
node packages/mcp-server/ab/compare-run.mjs --config /tmp/new-mcp-comparison/config.json
node packages/mcp-server/ab/compare-score.mjs --out /tmp/new-mcp-comparison/results
node --test packages/mcp-server/scripts/ab-compare.test.mjs
```

Нужен авторизованный `codex` CLI с поддержкой использованных параметров.
`default_tools_approval_mode="approve"` действует только на читающий MCP `ui`
в этом запуске; глобальные настройки пользователя не меняются.

Конфигурация, хэши пакетов/индексов/задач/prompt/раннера и полный порядок попыток
сохраняются в `manifest.json`. Продолжение разрешено только с тем же manifest;
готовые попытки не перезаписываются. JSONL-транскрипты, TSX, финальные JSON и
ошибки CLI сохраняются рядом с результатами. Для нового эксперимента нужен новый
каталог, а не удаление неудачных попыток.

## Дополнительная браузерная проверка

После фиксации основного плана, до анализа его итогов, добавлен дополнительный
smoke рендера. Все сгенерированные файлы проверяются без изменения кода в одном
потребительском приложении Vite с `GlobalStyle theme="light"`. Для каждой попытки
создаётся отдельный чистый browser context. Внешние сетевые запросы блокируются;
пользовательский профиль браузера не используется. Версии Chrome и Playwright
сохраняются в отчёте.

Критерий начального рендера: импортируется именованный компонент, React
монтирует непустое содержимое, нет pageerror/ErrorBoundary ошибки в течение
750 мс после готовности. Раннер сначала обязан принять обычный `Button`, форму с `useForm`/`FormProvider`/`FormTextField` и
отклонить компонент с намеренным `throw`, иначе весь smoke недействителен.
Зависимости разрешённого потребительского окружения заранее включены в Vite
`optimizeDeps.include`, чтобы поздняя переоптимизация не смешивала экземпляры React.
Это ловит падения импорта/рендера, но не доказывает доступность, внешний вид,
валидность данных или все взаимодействия.

Для трёх задач (`modal-confirm`, `modal-table-canvas`, `drawer-table`) есть ещё
один одинаковый для обеих версий шаг: открыть окно кнопкой и дождаться кнопки
«Отмена»/«Закрыть», а для drawer — также «Скачать», без падения рендера.
Кнопки открытия модальных окон берутся из текста исходной задачи; для drawer
используется первая кнопка исходного компонента. Это ограниченный smoke открытия,
а не проверка удаления договора, скачивания или содержимого всех строк таблицы.

```bash
node packages/mcp-server/ab/compare-render.mjs \
  --out /tmp/new-mcp-comparison/results \
  --browser '/path/to/chrome'
```

Нужны Vite и Playwright из зависимостей стенда; без `--browser` используется
Chromium, установленный Playwright. Итоги — `render-results.json`. Ошибки
намеренно остаются в результатах, не исправляются в ответах агента и не
передаются ему как обратная связь.
