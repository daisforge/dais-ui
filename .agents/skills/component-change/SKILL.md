# Изменение компонента

Общие правила (API, структура, стили, проверки) — в `AGENTS.md`. Здесь —
порядок работы. Не пропускай шаги 1–3: большинство регрессий появляется из-за
того, что код поменяли, не посмотрев, кто им пользуется.

## 1. Разобраться

- Найди компонент: MCP `daisforge-ui` (`get_component`, `get_component_props`)
  или `packages/ui-kit/src`.
- Определи вид: обёртка над sdds-finai, composition, standalone, form (см.
  `generators/meta-info/config/meta-config.json`). У обёртки сначала проверь,
  нет ли нужного пропа у самого атома sdds-finai.
- Найди использования: `rg "<Name>" packages/ui-kit/src packages/storybook/src`.
  Внутренние потребители ломаются так же, как внешние.
- Прочитай stories и тесты компонента — это его задокументированное поведение.

## 2. Для бага — воспроизвести

- Сначала тест (юнит или `play`), который падает на текущем коде. Если
  воспроизвести тестом нельзя — story и точные шаги.
- Ищи причину, а не место проявления. Исправление в одном месте не должно
  маскировать дефект в другом (например, `?.` или `|| 0` вместо выяснения,
  откуда пришёл `undefined`).

## 3. Зафиксировать API

Перед правкой выпиши текущий публичный контракт: `index.ts` компонента,
`types.ts`, значения по умолчанию (`constants.ts`, `defaultProps`,
деструктуризация с дефолтами), сигнатуры колбэков. Реши заранее, что из этого
меняется, и сверься с правилами API в `AGENTS.md`. Замену опубликованного
API делай только через этап `@deprecated`: старое остаётся работающим до major-релиза. Удаление
устаревшего и другие ломающие изменения — только в major по решению команды;
без явной просьбы предложи совместимый вариант.

## 4. Реализовать

- Структура — как в `AGENTS.md` и у ближайшего похожего компонента.
- Новый проп: опциональный, JSDoc с описанием и дефолтом, имя как у соседей,
  старое поведение без него не меняется.
- Контролируемый и неконтролируемый режимы: если у соседних компонентов есть
  пара `value`/`defaultValue` или `opened`/`onClose` — поддержи ту же схему.
- Эффекты — с очисткой (подписки, таймеры, `ResizeObserver`, слушатели).
  `window` и `document` — только в эффектах и обработчиках, не при импорте
  модуля.
- Колбэки в зависимостях хуков — стабильные (`useCallback`, `useRef`), чтобы не
  вызывать лишние перерисовки, особенно в `TableCanvas`.
- Не трогай файлы вне задачи. Нашёл проблему рядом — опиши в отчёте.

## 5. Тесты, stories, документация

- Тест на новое поведение и на сохранение старого (без нового пропа).
  Правила — скилл `write-tests`.
- Story на новый вариант; существующие stories не ломай — по ним сняты
  PNG-эталоны.
- MDX и JSDoc — скилл `generate-docs`. Новый компонент — запись в
  `meta-config.json` и экспорт в `packages/ui-kit/src/index.ts`.

## 6. Самопроверка

1. Проверки из таблицы в `AGENTS.md` для затронутых файлов.
2. Diff публичного API:

   ```bash
   git diff develop -- packages/ui-kit/src/index.ts \
     'packages/ui-kit/src/**/index.ts' 'packages/ui-kit/src/**/types.ts' \
     'packages/ui-kit/src/**/*.types.ts' 'packages/ui-kit/src/**/classNames.ts'
   ```

   Каждое изменение здесь должно быть намеренным и войти в отчёт.

3. Прочитай весь свой `git diff` глазами ревьюера по чеклисту скилла
   `code-review`. Убери отладочный код, лишние комментарии, случайные правки.

## 7. Отчёт

- Что сделано и почему так.
- **Изменения публичного API** — отдельным списком (или «API не менялось»).
- Какие проверки запущены и с каким результатом; что не проверено и почему.
- Риски и находки вне задачи.
