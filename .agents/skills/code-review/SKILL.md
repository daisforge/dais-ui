# Ревью кода

Цель — найти то, что сломает потребителей библиотеки или поведение
компонента. Стиль, который ловит ESLint и Prettier, не обсуждай.

## Что смотреть

- Свой diff: `git diff develop...HEAD` и незакоммиченное `git diff`.
- PR: `gh pr view <N>` (описание, цель) и `gh pr diff <N>`.

Читай не только строки diff: открой изменённые функции целиком, их
потребителей (`rg`) и связанные stories и тесты.

## Чеклист по приоритету

1. **Публичное API** (правила — в `AGENTS.md`). Изменились ли экспорты, пропсы,
   типы, дефолты, сигнатуры колбэков, `classNames`, реэкспорты sdds-finai?
   Новый проп назван как у соседних компонентов? Блокеры для API, которое
   уже вышло в опубликованной версии (добавленное после последнего релиза
   можно менять свободно, проверка — в `AGENTS.md`):

   - удаление, переименование, сужение типа, смена дефолта или поведения вне
     major-релиза — даже если старое было `@deprecated`;
   - замена API без этапа `@deprecated` (старое удалено сразу, а не помечено
     и оставлено работающим);
   - `@deprecated` без указания замены;
   - удаление `@deprecated`, которое не было помечено ни в одном
     опубликованном релизе;
   - ломающее изменение без строки `BREAKING CHANGE:` в теле коммита или без
     раздела «Миграция» в PR.

   Начинай с diff отчётов `packages/ui-kit/api/*.api.md`: удалённые и
   изменённые строки — кандидаты в блокеры, добавленные — новое API. Отчёты
   только генерируются (`npm run api:update`), поэтому их правка без изменения
   кода или сборки — ошибка. Исключение — отчёт в `develop` устарел после
   параллельных PR: тогда в описании PR должно быть это объяснение, а diff
   отчёта — совпадать с изменениями, которые уже есть в `develop`. Добавление и
   снятие `@deprecated` и изменения внутри типов sdds-finai в отчёте не видны —
   смотри исходники.

   Обновление `@salutejs/sdds-finai` и других runtime-зависимостей проверяй
   как изменение API: сравни реэкспортируемые типы и поведение (changelog
   зависимости, изменённые stories и тесты).

2. **Регрессии поведения.** Что будет у потребителя, который не знает об
   изменении: старые пропсы, неконтролируемый режим, пустые и `undefined`
   значения, длинный текст, большой объём данных, повторный рендер,
   размонтирование. Сохранены ли ветки, которые удалил автор?
3. **Корректность React.** Зависимости хуков, очистка эффектов, устаревшие
   замыкания, лишние перерисовки, `key` в списках, `window`/`document` при
   импорте модуля, `forwardRef` и `mergeRefs` не теряют ref.
4. **Тесты.** Есть ли тест на новое поведение и на исправленный баг? Проверяет
   ли он поведение, а не реализацию? Не ослаблены ли существующие тесты,
   допуски скриншотов, правила линтера?
5. **Соглашения проекта.** Токены вместо литералов, `$`-пропсы в styled, без
   `any` и `@ts-ignore`, структура папки, переиспользование утилит вместо
   дублей. В анимациях итоговое состояние задаёт стиль: нет `forwards`/`both`
   (в том числе в связке «базовая `opacity: 0` + `forwards`») и постоянного
   `will-change` без комментария, почему иначе нельзя (правило — в
   `AGENTS.md`).
6. **Доступность.** Роли, `aria-*`, фокус, клавиатура, `aria-label` у
   иконок-кнопок.
7. **Документация.** Stories и MDX для видимых изменений, JSDoc у новых
   пропсов, `meta-config.json` для нового компонента, сообщение коммита.

Если PR затрагивает скриншотные тесты или PNG-эталоны, прочитай
[инструкцию по скриншотам](../../../packages/storybook/test/screenshot-tests.md):
визуальные изменения должны быть намеренными, окружение — совместимым с
эталонами, а новые пропуски или допуски не должны скрывать дефект. PNG-skip
сохраняет render и `play`, но исключает визуальную проверку.

## Проверка находок

Каждую находку подтверди по коду: открой место, проследи данные, найди
потребителя. Не пиши «возможно, сломается» без сценария. Если проверить не
удалось — пометь как вопрос, а не как дефект.

## Формат

Сначала одна строка с вердиктом: можно мержить / после исправлений / нельзя.
Затем находки, от серьёзных к мелким:

```markdown
### [блокер | важно | мелочь] Краткая суть

`path/to/file.tsx:42`
**Сценарий:** входные данные или действия → что пойдёт не так.
**Исправление:** конкретно, что поменять.
```

Отдельным разделом — изменения публичного API, которые нашёл (даже
допустимые), чтобы автор перечислил их в PR.

## Чего не делать

- Не переписывай код за автора, если не просили, — только комментируй.
- Не предлагай архитектурных переделок при точечном ревью; крупное — отдельной
  рекомендацией в конце.
- Не дублируй замечания линтера и не придирайся к вкусовщине.
